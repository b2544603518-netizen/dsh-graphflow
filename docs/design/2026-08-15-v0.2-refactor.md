# dsh-graphflow v0.2.0 — 多智能体编排能力补全设计

> 日期：2026-08-15
> 依据：LangGraph 与 OpenAI Agents Python 的设计理念研究（两份独立评审），落到 DSH 既有接缝上做**无膨胀重构**。
> 结论主线：LangGraph 造 Send/子图/Store/流式是因为它底下没有平台；DSH 已提供 subagent / session / 审批栈 / 持久化 KV / workflow 工具，因此只借它的「执行模型 + Command」，其余照旧拒绝。

## 1. 目标与非目标

### 目标（v0.2.0，5 项，向后兼容 v0.1 的图定义）

1. **Command** —— 节点返回值升级：`State | Command`，一个返回值同时携带「状态更新 + 后继节点」。
2. **结构化 agent 输出** —— agent 节点声明 zod schema，子代理文本被校验为类型化 JSON 再进 channel；可选 `retries` 回喂重试。
3. **guard / abort** —— `NodeContext.abort(value)`，节点可带类型化原因终止整次 run（tripwire 语义）。
4. **checkpoint 历史 / 列表** —— 能列出一次 run 的 checkpoint 链（复盘/重放），为 v0.3 的 Send 铺路。
5. **agent 节点声明补全** —— 加 `name`（进 tracing 事件），其余 provider/model/prompt 已存在不动。

### 非目标（v0.2 明确不做）

- Send 动态扇出（v0.3 单独啃，按 barrier + fan-in 原则）
- 子图嵌套（agent 节点 → DSH subagent 已提供组合 + 隔离 + 可续聊）
- `Command.resume`（run 中途插入节点）
- 并行 guard、retry 策略库
- span/processor/exporter 可观测栈、长期记忆 Store 抽象、sessions 抽象
- handoff 历史过滤 / 压缩、context/DI 包装、每 LLM/tool 的 hook 分类

## 2. 能力设计

### 2.1 Command

**问题**：条件路由 `route(state)` 挂在边上，看不到节点内部产生的局部决策。

**设计**：
- 新增 `Command` 类（私有 brand 判别，避免与 state 字段撞名）。
- 构造：`new Command({ update?, goto? })`；`update` 折叠进 state，`goto` 指定下一个节点（可为 `END`）。
- 节点 `run` 返回类型扩为 `State | Command | Promise<State | Command>`。
- 后继解析优先级：`Command.goto` > 边；无 `goto` 时回退到边（完全向后兼容）。
- 校验放宽：节点允许 **0 条出边**（仅靠 `goto` 路由）；仍禁止单节点多出边。运行时「返回普通 State 且 0 出边且无 goto」才报错。

**Command 组合语义**：`update` 与 `goto` 相互独立，可只给其一。`update` 走与函数节点返回值相同的 reducer 折叠。

### 2.2 结构化 agent 输出

**问题**：引擎是「类型化 state + reducer」，但 agent 节点往 channel 里写未类型化文本，条件路由与 reducer 组合消费不了 LLM 结果。DSH subagent 只返回文本，平台不覆盖此点。

**设计**：
- `AgentNode` 加 `outputSchema?: z.ZodType`（zod 已在依赖）。
- 输出解析：子代理输出若已是 string 且 schema 为 string 类型 → 直接校验；否则 `JSON.parse` 后再校验。
- 校验失败：
  - `retries` 未设（默认 0）→ fail：`RunResult.error` 携带 zod issues（`code: 'agent_output_invalid'`）。
  - `retries: n` → 把校验错误回喂子代理重跑，最多 n 次；n 次后仍失败则 fail。
- 校验成功后写入 `key` 对应 channel，走该 channel 的 reducer。

### 2.3 guard / abort

**问题**：DSH 审批栈管「工具调用是否放行」，不管「内容级」校验（输入合规、输出合格）。

**设计**：
- 不加新节点 kind。`NodeContext` 加 `abort(value: JsonValue): never`，与 `interrupt` 对称。
- 执行器捕获 → 写 checkpoint `status: 'rejected'`（含 `abortValue`）→ 返回 `RunResult { status: 'rejected', abortValue, checkpointId }`。
- **guard 是文档化模式**：函数节点校验、不通过就 `abort`；input guard 放 agent 前、output guard 放 agent 后。

### 2.4 checkpoint 历史 / 列表

**问题**：`resume(任意 checkpointId)` 已支持时间旅行，缺的是「列出历史」的发现入口。

**设计**：
- `Checkpoint` 加 `step: number`（run 内单调递增，解决只有 `updatedAt` 时间戳会撞的问题）。
- `CheckpointStore` 加 `list(runId): Promise<Checkpoint[]>`。
  - `MemoryCheckpointStore`：内存按 runId 过滤排序。
  - `DomainCheckpointStore`：domain 加一张 `runs` 索引表（runId → [ckptId]），domain version 1 → 2。
- `GraphEngine` 加 `listCheckpoints(runId): Promise<Checkpoint[]>`。
- （`listRuns()` 原计划保留，但需存储层额外「枚举 key」接口且属次要能力，为遵守「别瞎增加」已砍掉；runId 本就来自每次 `run()` 的返回值。）

### 2.5 agent 节点声明补全

- `AgentNode` 加 `name?: string`，进 `graphflow/node-start` / `node-end` 事件 payload 与错误信息，人可读。

## 3. 兼容性与迁移

- 旧图（不写 `outputSchema` / `Command` / `name`）照常运行，语义不变。
- `RunStatus` 增加 `'rejected'`；`Checkpoint.status` 增加 `'rejected'`。
- domain version 1 → 2：v0.1 的旧 checkpoint 自然失效（项目仍是 pre-release，无真实持久数据）。
- 包版本 `0.1.0` → `0.2.0`。
